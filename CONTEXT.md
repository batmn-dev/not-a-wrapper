# Not A Wrapper

Domain language for the multi-AI chat app: one chat surface, many model providers, with tools layered on top of every conversation.

## Language

### Backend

**Convex module**:
The single server-side Convex source tree at `convex/`, including schema, functions, migrations, generated bindings, and Convex-domain tests. UI and component folders may import the root module's generated API, but must not contain copied Convex source trees.
_Avoid_: server copy, UI Convex mirror, `components/ui/convex`

**Authenticated handler**:
A Convex `query`/`mutation` defined through an auth-injecting builder (`authenticatedQuery`, `ownedChatMutation`, `ownedProjectMutation`, `ownedMcpServerMutation`, `ownedGenerationRunMutation`, …) instead of calling `ctx.auth.getUserIdentity()` inline. The builder resolves the caller's user — and, for owned-resource variants, fetches and ownership-checks the resource — before the handler body runs, injecting `ctx.user` (and `ctx.chat`/`ctx.project`/…) and enforcing one error contract (Not authenticated → not found → Not authorized). It makes auth structural, not a call you must remember. Ownership may be transitive: `ownedGenerationRunMutation` keys on a `runId`, fetches the **Generation run**, and resolves the owner through `run.chatId` (via the shared `requireOwnedGenerationRun`), injecting `ctx.run`/`ctx.chat`/`ctx.user`; its run-scoped handler bodies (`markGenerationRun*`, `updateAssistantSnapshot`, `createToolApprovalRequest`, `recordToolInvocations`) keep auth-free logic cores that take the injected `AuthenticatedRunOwner`, so a client-supplied `chatId` cross-check (`run.chatId !== args.chatId`) is structurally unrepresentable rather than hand-written. `prepareGeneration` stays on `ownedChatMutation` because it creates the run; `approveToolCall`/`denyToolCall` are self-identity-match on `approval.userId`, a distinct shape. Internal functions and the HTTP chat-route token path stay outside the seam; public-only reads (share links) and anonymous/optional-auth paths use their own non-throwing builders. Self-identity-match handlers (`identity.subject === arg`) are a distinct shape, not an owned-resource one.
_Avoid_: auth helper (the older bypassable `lib/auth.ts` form), middleware, guard

### Client

**Per-user subscription**:
The single client seam — a `usePerUserQuery` hook — every per-user Convex live read goes through. It owns the one correct subscribe gate, `isConvexAuthenticated` (the Convex JWT is synced), not WorkOS session presence (`!!user` / `!!userId`), and returns `"skip"` until it is true, so a signed-out or mid-auth-sync caller never opens a subscription or executes a wrong-empty read against a not-yet-resolved identity. It is the client counterpart to the **Authenticated handler**: the subscribe gate becomes structural instead of an `isAuthenticated ? {} : "skip"` ternary each call site re-derives with a different predicate (and which `userKeys.getProviderStatus` forgot entirely). Public/share-link reads go through a sibling `usePublicQuery` passthrough, and a `no-restricted-imports` rule bans raw `useQuery` from `convex/react`, so every call site declares per-user vs public — the same `maybeAuthQuery`-vs-`query` choice the backend makes. The hook returns auth-readiness alongside the data so providers stop re-deriving `data === undefined && authState` loading logic by hand.
_Avoid_: skip gate, auth ternary, guarded query

### Chat

**Chat turn**:
One user action that changes a conversation and may produce an assistant response: a new message, a suggestion send, a regeneration, or an edit. Edit and regeneration are server-owned variants — the backend creates a message branch and derives the new selected path — and may target any prior message, so they require a durable (authenticated, server-persisted) chat. Guest/local chats are send-only.
_Avoid_: submission, send flow, message lifecycle

**Chat turn runtime**:
The request-scoped server module that executes one **Chat turn**. `prepare()`
resolves the model and key, adapts history, prepares tools, and asks the
**Durable turn runtime** to enforce concurrency and create the generation run
before any model call. `toResponse(signal)` owns `streamText`, response shaping,
abort telemetry, and both stream-completion callbacks in one closure; durable
snapshot, approval, and terminal-write policy remain in the **Durable turn
runtime**. The route is only the HTTP adapter. The implementation still uses
the deprecated `result.toUIMessageStream(...)` instance helper; new work should
use standalone `toUIMessageStream({ stream: result.stream, ... })`. See
`docs/adr/0006-chat-turn-runtime.md`.
_Avoid_: chat handler, stream pipeline, request orchestrator (too vague); session (collides with the client `ChatSessionProvider` and the WorkOS auth session); Tool runtime (that is the composed sub-module, not this)

**Durable turn runtime**:
The second internal seam the **Chat turn runtime** composes (beside the **Tool runtime**) — the deep module (`app/api/chat/durable-turn-runtime.ts`) behind which ALL durable knowledge for one **Chat turn** lives: durable-prepare (the `prepareGeneration` call with approval-response extraction, latest-user-message selection, the argument-validation→400 mapping, and history canonicalization), identity answers (canonical model history; `originalMessages` + the assistant-message-id factory for the UI stream), the streamText extras (approval gating + the approval-persistence transform, its backpressure array now private), the write timeline (throttled snapshots, per-step tool-invocation upserts, terminal marks with the settle-approvals → flush → mark ordering), the finish handoff (`captureFinish` → `finalize`, replacing the three loose `durableFinal*` cells — a missed handoff is LOUD: `durable_finish_handoff_missed` warn + Sentry before the `countToolParts` fallback), and `fail(err)` legal at any phase. Two production adapters behind one selecting factory that internalizes `isDurableConvexChat` — the Convex adapter and the inert guest adapter — so the caller never asks "is this turn durable" and the convex token crosses once at construction. Consumes the Tool runtime through the `ToolFacts` port (`source`/`approvalFor`/`toolApproval`, structural, test-fakeable); the Convex wire stays a directly injected `fetchMutation` (no store port) and AI SDK shapes cross unwrapped. Await discipline is in the return types: `void` methods are fire-and-forget by contract, `Promise` methods must be awaited; double-terminal writes are not deduped client-side — the **Generation run lifecycle**'s first-terminal-wins absorbs them. Composed INSIDE `toResponse()`'s single closure — both onEnd layers still share it (ADR-0006 intact); the module names the handoff, it does not split it. See `docs/adr/0009-durable-turn-runtime.md`.
_Avoid_: session (banned collision); durable runtime (the old `durable-runtime.ts` helper file — vocabulary, not a module); persistence layer / store (it owns a timeline with ordering invariants, not passive storage); recorder (undersells the identity answers)
_Status_: implemented 2026-07-05 (branch `darknight/bat-signal-20260705-133514`).

**Chat turn controller**:
The client-side counterpart of the **Chat turn runtime** — the single React-free module (`lib/chat-turn/`, entry `chat-turn-controller.ts`) that executes one client **Chat turn** behind one adapters seam. It owns turn validation (length, generation-active, durable-only gates for edit/regeneration), optimistic frames and their rollback, the async run sequence (auth → limits → chat creation → uploads → dispatch), plan building (edit trim, regeneration target — `turn-plans.ts`), **Chat turn wire contract** body assembly, and guest/local persistence routing (`turn-store.ts`, composed INSIDE `createChatTurnController` — the parent hook supplies store adapters and never builds or holds the store). Runners read the **Turn context** snapshot at run time and see adapters live at call time, not construction time (callers may swap an adapter after constructing the controller). `use-chat-core.ts` is the React shell: it constructs the adapters from hook state and the AI SDK and calls the controller; `lib/chat-store/turns/` retains only the **Branch projection** (`selected-path.ts`).
_Avoid_: chat-turn-service (the old two-layer split: runners in `app/components/chat/chat-turn.ts`, builders in `lib/chat-store/turns/chat-turn-service.ts`), session (banned collision), parent-held turnStore (the store is internal), client chat turn runtime (runtime is the server module)
_Status_: implemented 2026-07-06 (branch `darknight/batwing`).

**Generation run**:
The durable record of one model-generation attempt within a **Chat turn** — created at durable-prepare, linked to the assistant message it streams into, carrying status (`queued → running → streaming → awaiting_approval | completed | aborted | failed`), usage, finish reason, and tool counts. One turn normally owns one run; regenerations and approval continuations create a new run against existing messages (the continuation closes the paused run via the **Generation run lifecycle**'s approvals-resolved signal).
_Avoid_: generation (ambiguous with the model call), stream (that's the transport), job

**Generation run lifecycle**:
The single pure domain module (`convex/domain/generation_run_lifecycle.ts`) owning the legal transitions of a **Generation run** and its paired assistant message. Signal-shaped: `resolve(current facts, signal) → verdict`, where signals are `complete / fail / abort / supersede / approval-requested / approvals-resolved` and the verdict names the run patch plus the message resolution (stamp, keep **Terminal outcome stub**, delete-and-reselect sibling, restore-completed for a regeneration that died pre-snapshot). Owns the race rules in one table: first terminal outcome wins; failed may overwrite completed (the onError-vs-envelope race must converge to failed) but never aborted (user Stop is settled); completion downgrades to awaiting_approval while approvals pend; supersede reaches only queued/running/streaming (paused runs are closed by deny-pending at next-turn prepare, never swept). Mutation handlers gather facts and apply patches; they do not re-derive legality.
_Avoid_: state machine helper, status guard, transition utils (all too vague — this is the one brain, not a helper)
_Status_: implemented 2026-07-05 (branch `darknight/bat-signal-20260705-133514`).

**Terminal outcome stub**:
An empty assistant message kept (not deleted) with a terminal status (`failed`/`aborted`) when a run dies before producing content and no semantic sibling exists to fall back to. It renders as an inline failed/stopped state with retry, projects into model history as an explicit "never answered" marker, and is counted symmetrically by client and server visibility (the **Selected path token**'s two-pass validation exists so a stub materialized by the supersede sweep never falsely rejects the turn that triggered it).
_Avoid_: empty placeholder (that's the pre-terminal state), ghost message, deleting failed turns (the bug this fixes)

**Message branch**:
A sibling message alternative under the same parent message, created by durable edits and regenerations so prior turns remain addressable instead of being overwritten or deleted.
_Avoid_: fork (too broad), version (too overloaded)

**Message branch writer**:
The single mutation-scoped Convex module that commits complete **Message branch** changes through three role-shaped operations: write an idempotent user message, write an assistant placeholder, or select an existing branch. It owns legacy normalization, effective-parent resolution, sibling selection, sparse-safe branch-index and message-order allocation, insertion, and post-write **Selected path** validation; callers retain ownership and optimistic-concurrency checks, approval and title policy, **Generation run** creation, and model-history projection.
_Avoid_: branch-write helpers (the shallow primitives it replaces), generic insert/select command (leaks user-message idempotency), message store (it owns branch invariants, not passive persistence)
_Status_: implemented 2026-07-11 (branch `darknight/janus-cosmetics`).

**Selected path**:
The backend-derived linear path through a chat's message branches used for rendering and model history. Hidden sibling branches stay stored but are not sent to the model until selected.
_Avoid_: visible messages, active transcript

**Branch projection**:
The single client seam that installs the backend's selected path into the AI SDK's flat `useChat` array while a chat is idle: it adopts server ids and branch state onto matching live messages, preserves in-flight optimistic sends, and swaps wholesale when the path diverged (a branch switch, or restoring messages a rejected edit/regeneration sliced out). It is the sole owner of client identity adoption — matching by message identity across the full selected path (not a positional tail patch) and reading server ids through one typed accessor (`readServerMessageId` in `lib/chat-messages/branch.ts`). The client renders the server's selected path; it does not re-derive it. See `docs/adr/0001-client-renders-server-selected-path.md`.
_Avoid_: reconcile (too narrow — that's only the id-adoption half), rehydrate, sync

**Message metadata module**:
The single client module (`lib/chat-messages/metadata.ts`) that owns message `metadata`: one private set of server-owned keys, the `isRecord` guard, and the typed readers/writers (`getServerMessageId`, `getBranch`, `stampServerFields`, `adoptServerOwned`) every caller goes through instead of casting `metadata as Record<string, unknown>` and hand-poking keys. The durable adapter and the branch projection call its writers; renderers call its readers. The streamed assistant-metadata blob is projected through a named validator (`vToolInvocationStreamMetadata`, `convex/lib/messageMetadata.ts`) at the persist boundary so only the owned key-set is written and malformed writes are rejected; the storage column (`messages.metadata`) is narrowed to that same validator so the stored shape is provably the owned key-set, not an opaque `v.any()`. Branch stays a transient, droppable descriptor; the writers preserve reference identity on no-op (the projection's idempotence contract) and pass client-transient keys (e.g. `reasoningDurationMs`) through untouched.
_Avoid_: metadata bag, ad-hoc cast, `metadata as Record`

**Selected path token**:
The forward (client→server) staleness guard for a chat turn — a `{ expectedVisibleMessageCount, tailMessageId? }` descriptor the client derives from the rendered selected path and sends with a new-message turn; the backend validates it before mutating and rejects a turn raced against a changed selected path. It is the counterpart to the branch projection (the backward, server→client half) and is unrelated to it despite the shared name; edits and regenerations carry their own count guard (`expectedChatVersion`) instead of the token.
_Avoid_: conflating with branch projection (that's the backward half), version (overloaded)

**Chat turn wire contract**:
The single statement of the `POST /api/chat` request shape (`lib/chat-messages/chat-turn-contract.ts`), imported by both sides of the HTTP seam: the client turn builders produce `ChatTurnBodyFields` (the AI SDK transport merges in `messages`), and the chat route validates the result through `parseChatTurnRequest` — required fields, edit⊕regeneration exclusivity, and the guest-id rule — before constructing the **Chat turn runtime**'s input. One declaration, so a field added or renamed on one side is a compile error on the other. The contract is closed (no extras spread or index-signature escape hatch — a new wire field is added here first) and carries the trust taxonomy in one place: caller identity is session-derived server-side (ADR-0010), `userId` is read only as the guest rate-limit key, and `isAuthenticated` deliberately does not exist on the wire. Edit and regeneration cross as `ChatTurnEditRequest` / `ChatTurnRegenerationRequest` — the same names on both sides; the **Selected path token** crosses spread flat into the body fields.
_Avoid_: per-side request types (`ChatRequest` vs `ChatTurnRequestBody`, the pre-contract duplication), intent-vs-request split naming (`ChatTurnEditIntent`), `bodyExtras` / body index signature (the escape hatch this closes), sending `isAuthenticated` in the body (identity is never body-derived)
_Status_: implemented 2026-07-06 (branch `darknight/batwing`).

**Chat list window**:
The bounded, recency-ordered slice of a user's chats the **sidebar** subscribes to — a `usePaginatedQuery` of **non-pinned, non-project** chats over the composite `by_user_pinned_project_updated` index (`getRecentWindowForCurrentUser`), plus a small live pinned read (`by_user_pinned`), behind `ENABLE_PAGINATED_SIDEBAR` (ADR-0005). Pinned/project chats are excluded at the index level so they never consume a window slot. It is deliberately NOT the full chat list: a chat write invalidates only the window, not the whole `by_user` collection. The client `useChats()` store narrows to this window; the id-keyed optimistic overlay applies to it, so an op on a chat outside the window is a no-op in the sidebar (the surface that shows that chat reflects it via its own read). `isLoading` from the store means "first window page ready," not "all chats loaded." Per-chat access outside the window goes through `useChat(chatId)` (a targeted `chats.getById` fallback), and `chats.updatedAt` is the single activity field the window orders by — one bump per durable turn, at turn start.
_Avoid_: the full chat list, `getForCurrentUser` as the sidebar source (that is the pre-ADR-0005 unbounded read), recent chats (ambiguous)

**History search**:
Full-history reach that does NOT go through the **chat list window** — the surfaces that must see chats outside the bounded sidebar, each on its own on-demand read: title search (`chats.searchByTitle` over a `by_title` search index, subscribed only while the search UI is open, behind a `SearchProvider` that exposes `query → results`), browse-all (a paginated non-project `by_user_project_updated` read in the history drawer, because project chats are hidden while browsing), the project view (`getProjectChatsForCurrentUser` over `by_project`), and deep-links (`useChat` → `chats.getById`). Search is title-only by design and still reaches project chats; message-content search would be a separate index on `messages`. These reads are what make bounding the sidebar safe — they each own full-history access rather than borrowing the sidebar's list.
_Avoid_: searching the sidebar window (it is bounded; search must hit its own server read), the full array (the search provider exposes results, never the corpus)

**Sidebar row**:
The single client module the **sidebar**'s chat and project lists both render through — the deep module behind the editable/navigable compact row. It owns the structural invariants the two lists otherwise copy: the editing⇄resting mode swap, inline rename (`useInlineRename` held internally), the `containerRef` click-outside-commit wrapper, and the single-`<Link>` nested-anchor recipe (trailing actions nest inside the anchor; `preventDefault`/`stopPropagation` open the menu without navigating — the "dead corners" fix), plus the `.sidebar-row menu-item-hoverable` container recipe, the active-state token, pointer-coarse sizing, mobile-close-on-nav, and the reveal-by-reflow trailing slot (the reveal keys off `.sidebar-row`, so the old per-row `group/chat`·`group/project` scope names are vestigial). Domain glue stays in two thin adapters — chat (`updateTitle` + status/pin/`SidebarItemMenu`) and project (`updateName` + `SidebarProjectMenu`): each supplies `href`, `isActive`, an optional `leading` node, `renameValue`/`onRename` (persistence + error handling), and a **render-prop** `trailing({ startRename })`. The render prop is load-bearing: the trailing menu must trigger rename while `useInlineRename` stays inside the module. The bordered project-chat **card** (date subtitle, distinct resting presentation) is deliberately NOT this module — it shares only `useInlineRename`; the history-drawer row is a separate edit idiom and stays out until the history surfaces are unified.
_Avoid_: per-entity row components (the triplicated `SidebarItem`/`SidebarProjectItem`/`ProjectChatItem` scaffold this replaces), a wide props-bag row (leading+title+trailing+href+active+menu forwarded to a div — shallow), threading `start`/`onStartEditing` back out to the caller (the render-prop keeps rename inside)
_Status_: implemented 2026-07-08 (branch `darknight/wayne-foundation`; `sidebar-row.tsx` shell + chat/project adapters; card + history-drawer scoped out).

**Provider-key panel**:
The single client module both key-management settings surfaces run through — BYOK model-provider keys (`apikeys/byok-section.tsx`) and third-party tool keys (`tools/tool-keys.tsx`). A deep hook (`useProviderKeys`) owns the shared spine: provider selection, the draft buffer + masking (per-provider `maskHint`, cleared on focus), and the save/delete mutations against `/api/user-keys` with their toasts and the "never persist the mask or an empty field" guard (which also fixed BYOK's old untouched-Save-posts-the-placeholder-dots path). It is provider-domain-free: key presence arrives as `keyStatus` (the model store's `userKeyStatus`, whose index signature keeps it a plain `Record`) and side-effects cross as the `onSaved`/`onDeleted` ports — BYOK passes `refreshAll` + favorites invalidation; tool keys pass none (the subscription auto-updates). A `<ProviderKeyPanel>` renders the shared chrome — the key-input form, the "Get API key" link, the save/delete buttons, and the one delete-confirmation dialog — with the provider tile as a render-prop slot, because the two tile presentations (BYOK's icon grid vs the tool rows with status/description/cost) are genuinely different. Each caller is a thin adapter: its provider config array, its tile, its copy, and its side-effect ports.
_Avoid_: two per-surface key panels (the ~390-line `ByokSection`/`ToolKeys` copies this replaces), a wide props-bag panel, baking both tile presentations into the panel (the tile is a slot), hardcoding `refreshAll` in the shared module (it crosses as the `onSaved` port). The three parallel provider _lists_ (`lib/providers` + the two adapters' arrays) remain — unifying them is the **Provider identity** deepening (see Models).
_Status_: implemented 2026-07-08 (branch `darknight/wayne-foundation`).

**Row-actions menu**:
The single dropdown both row menus run through — the chat menu (`chat-actions-menu.tsx`) and the project menu (`sidebar/sidebar-project-menu.tsx`). `RowActionsMenu` (`layout/row-actions-menu.tsx`) owns the scaffold the project menu used to fork: the ⋯ trigger chip (`trailingIconButtonClassName` + `TrailingIconChip`, with the nested-anchor `preventDefault`/`stopPropagation`), the mobile-safe `DropdownMenu` (`modal={isMobile}`), and the `animated={false}` content, rendering items from a config array (`RowActionItem` — `{icon, label, onSelect, variant?, loading?, disabled?}`; `icon` is a ReactNode so both `<Icon>` and lucide glyphs work; `loading` swaps a spinner). Each caller is an adapter: `ChatActionsMenu` builds Share/Pin/Rename/Delete and owns its handlers, `DialogDeleteChat`, and `SharePublishDrawer`; `SidebarProjectMenu` builds Rename/Delete and owns `DialogDeleteProject`. Confirmation dialogs stay in the adapters (a "Delete" item just fires `onSelect`); unifying the dialogs is a separate deepening. `SidebarItemMenu` stays a thin pass-through onto `ChatActionsMenu`.
_Avoid_: rebuilding the dropdown scaffold per row kind (the `SidebarProjectMenu` fork this replaces), a dialog slot in the menu (dialogs stay in adapters), threading a controls object instead of an items config.
_Status_: implemented 2026-07-08 (branch `darknight/wayne-foundation`).

**Disclosure card**:
The single collapsible card the chat surface uses for tool steps and sources (`app/components/chat/disclosure-card.tsx`) — a bordered box + hover header + rotating down-chevron + framer height-spring reveal. It owns the structural invariants three sites hand-rolled (the multi-tool box and the single-tool view in `tool-invocation.tsx`, plus `sources-list.tsx`, each re-declaring the same `TRANSITION` spring): the box, the header button (now carrying `aria-expanded`), the chevron, the `useState` toggle, the `AnimatePresence` reveal, and the `px-3 pt-3 pb-3` body padding. Callers pass a `header` slot + body and keep their own outer margin wrapper. Deliberately framer-based — matching the chat surface's idiom — rather than built on the base-ui `Collapsible`/`CollapsibleSection` (CSS-keyframe, right-chevron, borderless, localStorage) the sidebar/settings use; the two treatments are genuinely different, so they stay distinct primitives.
_Avoid_: re-hand-rolling the box+header+chevron+reveal per site (the three copies this replaces), a duplicated per-file `TRANSITION` const, forcing the chat disclosures onto `CollapsibleSection` (different treatment). The orphaned `components/motion-primitives/disclosure.tsx` was NOT adopted (its `DisclosureTrigger` spreads child props over the injected handlers and would double-toggle a native `<button>`) — it is a dead-file-sweep candidate.
_Status_: implemented 2026-07-08 (branch `darknight/wayne-foundation`).

**Assistant turn view**:
The single pure derivation of everything renderers need from one assistant message — text, attachments, tool parts and their render signature, sources, image-search results, and normalized reasoning evidence (ordered displayable blocks, observed opaque activity, literal streaming state, and persisted duration read via the **Message metadata module**). Derived per render in Conversation's map loop, never memoized by `parts` reference (the AI SDK mutates part objects in place during streaming), and consumed by the message row and **Activity panel** alike. The live reasoning timer runs only from literal observed reasoning, not from the generic Thinking status, and server duration becomes terminal authority when it arrives.
_Avoid_: per-renderer part extraction (`parts?.some(...)` in components), raw `metadata.reasoningDurationMs` / `metadata.toolMetadataByName` reads (go through the metadata module's readers), view model (Reactism)
_Status_: implemented 2026-07-03 (branch `darknight/gotham-by-gaslight`).

**Assistant turn phase**:
The single canonical answer to "what is this turn doing right now?" — a discriminated union (`submitted → thinking(visible|opaque) → generating-image → tooling(toolNames) → awaiting-approval → responding → settled`) derived by one pure first-match ladder in `lib/chat-messages/assistant-turn.ts` from the **Assistant turn view** plus one liveness fact (`isLast` + the row render status). A bare active stream stays `thinking`; there is no separate Generating/caret phase. Liveness rules are unchanged: only the last turn owned by this client's submitted/streaming status is live, while frozen historical and terminal part states settle immediately.
_Avoid_: per-affordance boolean gates (`showDots`/`showToolProgress`-style pairwise suppression), reasoning opacity as a proxy for "reasoning is visible on screen", trusting durable live statuses or frozen part states for liveness, a second loader rendered outside the indicator slot
_Status_: updated 2026-07-10.

**Assistant activity presentation**:
The provider-neutral presentation source of truth in `lib/chat-messages/assistant-activity.ts`. It converts an **Assistant turn view** plus phase into exactly one closed variant: `none`, non-interactive `live-status`, passive completed timing, or an inspectable `disclosure` carrying a statically non-empty section tuple. `Thinking` is the universal content-empty live label; normalized tool facts may replace it with search, image, approval, or named-tool copy without changing the renderer. Completed duration is finite, non-negative, hidden below 1000ms, and floored thereafter. Visible reasoning, sources, tool steps, approvals, images, and tool errors become sections; opaque reasoning never becomes an empty Reasoning section. Only disclosures render a button, chevron, `aria-expanded`, or `aria-controls`.
_Avoid_: raw-part inspection in components, provider-name label branches, `Math.round` duration labels, focusable passive timing, disclosures with empty sections
_Status_: implemented 2026-07-10.

**Activity panel**:
The Chat-hosted module behind the single activity surface (reasoning, sources, tool steps) — one panel instance, one open state, one projected turn. Assistant rows reach it through a store seam with per-row selectors (`isPanelTurn(messageId)`-shaped reads) and stable action identities (`openTurn`, `close`), not via a controls object threaded Chat → Conversation → Message → MessageAssistant. The explicit-vs-default turn classification (`selectExplicitActivityTurnOnOpen`) resolves inside the store at call time from current state — never from a closure captured at render time, the stale-closure class that the prop thread invited. A panel handoff re-renders only the two affected rows (old and new panel turn), and the scroll-anchoring release on open stays internal to the module. The pure target selector (`selectActivityPanelTarget`) and its tests survive as the selection brain.
_Avoid_: `activityPanel` prop threading, controls-object forwarding, re-deriving `isPanelTurn` in rows, memo comparators peeking into panel fields
_Status_: implemented 2026-07-03 (branch `darknight/gotham-by-gaslight`).

**Turn context**:
The per-chat client module owning the inputs every **Chat turn** kind needs at run time: selected model (chat model → last-used → favorite → tier default resolution, override cleared on chat navigation), web-search enablement, and system prompt. Turn runners (send, suggestion send, edit, regeneration) read it through an imperative snapshot getter at run time — not through closure-captured values that go stale between render and submit (the `?prompt=` auto-submit-before-hydration wrong-model case). The **Composer** renders the model picker and search toggle as writers of this module; edit and regeneration consume the same snapshot, which is why the module is chat-level, not composer-private. Snapshot exposes hydration readiness so auto-submit can wait.
_Avoid_: closure-captured model/search in submit callbacks, three-layer model ownership (hook logic + Chat orchestration + input pass-through), composer-owned model (edits/regens need it too)
_Status_: implemented 2026-07-03 (branch `darknight/gotham-by-gaslight`).

**Composer**:
The deep client module that assembles a **Chat turn** payload: it owns the draft (per-chat persistence and clearing), attachment files, suggestion UI, paste/drop capture, and the primary action, and emits one complete payload (`text`, `files`) through a single `onTurn` interface — Chat decides when and how to run the turn. External commands come through a small imperative handle (`insertQuote`, `setText`, `focus`) instead of command-as-state props (`quotedText`) and listener-registration plumbing. It reads auth from the user store and model/search from the **Turn context** directly, so the parent stops threading orchestration props (the 21-prop interface and its 18-dependency memo dissolve).
_Avoid_: chat-input prop orchestration (the shallow 21-prop interface), parent-owned draft/file state, `quotedText`-style commands modeled as state
_Status_: implemented 2026-07-03 (branch `darknight/gotham-by-gaslight`).

### Tools

**Tool runtime**:
Everything a chat request needs to use tools, prepared once per request and alive for the whole stream: the merged tool set, per-tool metadata, step gating, budget accounting, and tool outcome recording.
_Avoid_: tool coordinator, tool orchestrator, tool loader

**Tool layer**:
One of the sources tools come from — Layer 1 (provider-native), Layer 2 (Exa search/content fallback), Layer 3 (user-configured MCP servers). Layers are merged into the tool runtime; later layers win name collisions.
_Avoid_: tool source (reserved for the per-tool metadata field), tier

**Capability policy**:
The per-request decision of which tool capabilities (search, extract, mcp, code) a user/model/key combination may use, and which specific tools are allowed in early vs late steps.
_Avoid_: permissions, feature flags

**Tool budget**:
The per-tool call allowance enforced during a request — probed before provider-executed calls, consumed after execution, degrading to a request-local soft cap when the policy store is unreachable.
_Avoid_: rate limit, quota

**Tool outcome**:
One record per tool call — tool identity and display name, source, success, duration, error, budget fields, input/output previews, token usage — assembled by the tool runtime when the call's step finishes and pushed through outcome sinks injected at preparation (audit log, analytics, trace log). Every call produces an outcome, including failures and tools the runtime cannot identify; errors are recorded for all sources. The runtime accumulates outcomes and exposes a request-level summary.
_Avoid_: tool call log entry (that's one sink's projection), tool trace (reserved for the in-flight timing/error data the outcome consumes), tool result (reserved for the provider's result payload)

### Models

**Vendor**:
The open-set presentation identity of a model's maker — an icon plus display name (`claude`, `gemini`, `grok`, `deepseek`, `meta`, `qwen`, …) — distinct from **Provider**, the closed key-bearing API surface that has a **Provider strategy**. The catalog's `icon` and `baseProviderId` fields point into vendor space, not provider space; wrapped OpenRouter models carry real vendor ids without registered icons and fall back to the OpenRouter icon. Known vendors live in the **Provider identity** module's vendor registry; icons live in a client-only sibling registry keyed by the same vendor ids so server code never imports React components.
_Avoid_: brand (rejected — clashes with `baseProviderId` naming already in the catalog), provider (reserved for the key-bearing surface), conflating the two in one list (the pre-unification `PROVIDERS` array mixed both vocabularies untyped)

**Provider identity**:
The single server-safe module (`lib/provider-identity.ts`) owning what is identically true about a key-bearing provider everywhere it appears: the `Provider` and `ToolProvider` id unions (and their `KeyedProvider` union — both kinds share the encrypted `userKeys` storage), each provider's company display name (key-settings tiles use the company identity — Anthropic, Google, xAI — never the product brand; model rows keep **Vendor** identity), the provider→vendor link, the key-setup facts (placeholder, get-key URL, mask hint; for tool providers also description, cost estimate, availability, and env-var name), and the known-vendor registry. Icons are the one client-only sibling (`lib/provider-icons.tsx`), keyed by vendor id. Deliberately excludes the **Provider strategy**'s static SDK facts — the model-provider env-var name stays on the strategy; identity is what the UI and key storage agree on, not how an SDK is constructed. The ADR-0007 snapshot generator derives each model's `provider` display name from this module and validates `providerId`/vendor ids at generation time, so a provider that exists in the runtime union but is missing from key settings (or vice versa) is a failing inventory test, not a shipped inconsistency.
_Avoid_: three parallel provider lists (`lib/providers` + the two key-panel arrays — the drift this replaces), aliasing one provider to its product brand in key settings (the old anthropic→"Claude" tile), `Provider.id: string` (the untyped conflation), re-homing `envVarName` for model providers (strategy-owned)
_Status_: implemented 2026-07-11 (branch `darknight/janus-cosmetics`).

**Provider strategy**:
The single home for everything statically true about one model provider's AI SDK: how to instantiate its client (a BYOK key vs the provider's default/env credentials), its optional native built-in search tool plus that tool's display metadata, and its platform API-key environment-variable name. Stateless; one per provider, behind a registry keyed by `getProviderForModel` (`lib/openproviders/provider-strategy.ts`). The same instance backs both the language model and the search tool, so tool calls structurally bill to the same key as the model — the BYOK billing invariant is no longer a hand-synced convention split across the model factory and the tool factory. `languageModel` is synchronous (the registry is statically constructed; provider SDKs are eagerly imported, because model construction must return a non-Promise `ProviderLanguageModel` — the `LanguageModelV4 | LanguageModelV3` union that exists only because OpenRouter's community provider has no v4-spec release; see the TODO(openrouter-v4) tracking note in `provider-strategy.ts` for what the V3 path silently degrades). It deliberately excludes anything that is not a static SDK fact: routing (`getProviderForModel` is the selector that reads catalog membership, which the strategy does not own), key selection/precedence (the strategy declares only the env-var name; `getEffectiveProviderApiKey` consumes it and returns the authoritative BYOK/platform source), request shaping (per-model request policy — stays a free function), and history adaptation (a sibling seam with a different, non-1:1 taxonomy). OpenRouter is the documented irregular — self-resolved env, `.chat()`, `openrouter:` prefix strip, no native search — with every divergence body-internal so the shared interface never widens.
_Avoid_: provider wrapper, provider factory (too narrow — that is only `languageModel`), provider adapter (reserved — the history-replay adapters are a different seam)

**Request shaping**:
Everything provider-specific about issuing one model request, resolved from the model config plus request context (active search tools, tool presence): provider options such as thinking/reasoning configuration, per-model thinking budgets, and provider beta headers. Owns provider-workaround invariants (e.g. SDK pause_turn downgrades) so callers never branch on provider. Stays a free function keyed by `providerId`, deliberately outside the **Provider strategy**: its variation is per-model and per-request (the reasoning-text gate, the search-active thinking downgrade, the token-efficient header), not a static provider fact.
_Avoid_: provider options (reserved for the AI SDK field it produces), model tuning
